MCPDB Thinking Engine

A multi-mode reasoning engine that translates natural language questions about data into executable analysis plans, runs them in a secure sandbox, and synthesizes human-readable reports with visualizations.

Overview

MCPDB is a natural language data exploration system built as an MCP (Model Context Protocol) server. At its core is a thinking engine — an agentic graph that classifies questions, generates multi-step execution plans, runs SQL and Python code against live data sources, handles errors through self-debugging, and produces synthesized answers with charts and tables.

Design Principles

Graph-based Orchestration

Inspired by LangGraph, the engine uses directed graphs of async nodes with typed state. Each mode is a subgraph with conditional edges, retry loops, and escalation paths.

Mode-adaptive Thinking

Questions are classified into modes of increasing complexity. Simple questions get fast answers; complex research questions trigger multi-investigation pipelines with reasoning loops.

Self-correcting Execution

Failed code steps are debugged by the LLM, which sees the error, prior context, and schema — generating corrected code. Anti-pattern tracking prevents repeated mistakes.

Secure Sandbox Isolation

All generated code runs in subprocess sandboxes with AST-validated imports, memory/CPU limits, and a strict allow/block module policy. No file system or network access.

Experience Cache Replay On a cache hit, MCPDB does not simply return the cached text. It re-executes the cached code steps against live data (in case data has changed) and then re-synthesizes the response. If the schema has drifted (detected via schema fingerprint), the cache entry is invalidated.

Mode System

Mode Taxonomy

Modes are divided into two categories: base modes that directly execute analysis, and metamodes that orchestrate multiple base-mode runs.

Mode Type Steps Description
quick Base 0 Answers from schema context or prior conversation — no code execution. Auto-escalates to simple if it can't answer.
simple Base 1–5 Default mode. Generates a plan, executes SQL/Python steps, debugs errors, validates, synthesizes. Handles most data questions.
extended Base 3–10 Multi-phase analysis with checkpoint reviews. LLM reviews progress after each phase, can revise direction. Max 2 revisions.
optimization Base 1–5 Cost-gated execution for large tables (>1M rows). Asks user to confirm before expensive operations. Generates optimized queries.
deep Meta 2–5 investigations Research mode. Creates a blueprint of sub-questions, classifies each into a base mode, runs them with reasoning checkpoints, synthesizes a comprehensive report.
sequential Meta 2–20 questions Answers a list of questions one-by-one with accumulating context. Each sub-question is independently classified into a base mode.

Question Classification

Classification happens in two tiers: a fast-path regex check for obvious patterns, and an LLM classification for everything else.

Fast-path Patterns (no LLM call)

  • Quick: questions about tables, columns, schema, ERD, foreign keys, relationships
  • Off-topic: greetings ("hello", "bye"), meta-questions ("who are you?")

LLM Classification

The LLM receives the question, schema context, and mode descriptions. It returns a JSON with mode, reasoning, target_sources, requires_cross_source, and key_entities.

Key guardrail: questions requiring computation, counting, or data analysis are never classified as quick — they must be simple or higher.

Metamode Architecture

Metamodes use classify_question(allowed_modes=BASE_MODES) to restrict sub-question classification to only base modes, preventing recursive metamode dispatch (e.g., a deep investigation spawning another deep investigation). The shared dispatch_base_mode() utility routes the classified sub-question to the correct runner.

# Metamode restricts classification to base modes only
classification = await classify_question(
    question=sub_question,
    source_context=state["source_context"],
    llm=llm,
    allowed_modes=BASE_MODES,  # {quick, simple, extended, optimization_required}
)

# Dispatch to the classified base mode
state = await dispatch_base_mode(state, llm, callbacks, registry)

Planning

The planner generates a structured JSON plan with typed steps. Each step specifies an action type and the code to execute.

Step Types

ActionDescriptionExecution

Plan Retry Strategy

If the LLM fails to generate a valid plan, a 3-tier fallback activates:

  1. Primary LLM with full prompt
  2. Simpler LLM call (reduced prompt)
  3. Hardcoded fallback plan — schema introspection + sample query

Execution

Each plan step is executed sequentially. SQL queries run through SQLAlchemy; Python code runs in a subprocess sandbox. Results flow forward as context for subsequent steps.

DataFrame Variable Convention

The plan prompt instructs the LLM to use df as the standard variable name. The execution engine makes prior step results available as df in subsequent Python steps, enabling natural chaining:

# Step 1 (SQL): SELECT * FROM orders WHERE amount > 100
# → result stored as df

# Step 2 (Python): uses df from Step 1
import matplotlib.pyplot as plt
df.groupby('region')['amount'].sum().plot(kind='bar')
plt.title('Revenue by Region')
plt.show()  # captured as base64 PNG artifact

Self-debugging

When a step fails, the debug node provides the LLM with the failed code, error message, schema context, and anti-pattern hints. The LLM generates corrected code. Each step gets up to max_retries debug attempts (default 3, reduced to 2 for sub-investigations).

Anti-pattern Integration If the same error type has occurred before on this data source, the anti-pattern tracker injects avoidance hints into the debug prompt: "Previous failures suggest: check column names for this table — they use Hungarian naming conventions."

If all retries are exhausted, the step is advanced past (not fatal) — the pipeline continues with remaining steps, and the synthesizer notes the gap.

Validation

After all steps complete, the validation node asks the LLM: "Given these execution results, does the data adequately answer the question?"

Three possible outcomes:

  • Adequate: proceed to synthesis
  • Inadequate: trigger replan with the LLM's suggested improvements (up to 1 replan)
  • Partial: synthesize with what we have, noting limitations

Synthesis

The synthesizer converts raw execution results into a human-readable markdown response. It receives the original question, all step results, and any validation notes.

Fast-path Synthesis

For simple results (≤2 tables, ≤50 rows), synthesis skips the LLM entirely and formats the data directly as markdown tables — faster and more accurate than LLM reformatting.

Artifact Handling

Charts captured from plt.show() in the sandbox are encoded as base64 PNGs and attached as artifacts. The web UI renders these inline; exports embed them in HTML/PDF/Jupyter.

Deep Analysis Mode

Deep mode is a research-grade metamode for comprehensive, multi-angle investigations. It creates a blueprint of sub-questions, runs each as an independent investigation through a classified base mode, performs reasoning checkpoints to evaluate sufficiency, and synthesizes a structured research report.

Blueprint Creation

The LLM acts as a "senior data analyst" creating a research blueprint with:

  • A clear research goal
  • 2–5 investigations, each with a sub-question, approach, and priority
  • At least one investigation requiring data visualization
  • Non-overlapping, independently executable sub-questions

Key Design Decisions

  • Streaming-first: All providers implement stream() as the primitive. generate() and generate_json() are built on top by consuming the stream.
  • Robust JSON extraction: _extract_json() handles LLMs that wrap JSON in markdown fences, trailing text, or malformed output. _repair_json() fixes common issues (trailing commas, unquoted keys).
  • API key auto-resolution: The factory looks up environment variables automatically (GEMINI_API_KEY, ANTHROPIC_API_KEY, etc.) without explicit configuration.
  • No hardcoded max_tokens: Provider defaults (16384) are used everywhere for consistent behavior.

Database Sources

SQLAlchemy engine with connection pooling (5 connections, pre-ping, 1-hour recycle). Supports PostgreSQL, MySQL, SQLite, MSSQL, Oracle via dialect-specific adapters. Schema introspection discovers tables, columns, types, row counts, primary and foreign keys.

CSV Sources

Files loaded into an in-memory DuckDB instance for SQL querying. Auto-detects encoding (chardet), delimiter, and header presence. Multiple CSV files join into a single queryable source.

Excel Sources

Parsed with openpyxl for structure analysis (table boundaries, formula clusters, dependency graphs). Detected tables are extracted as DataFrames and registered in DuckDB. Implements both QueryableSource (SQL) and SpreadsheetSource (cell-level access).

Mode Hierarchy for Cache Filtering

Cache lookups respect a mode hierarchy: quick (0) < simple (1) < optimization (2) < extended/sequential (3) < deep (4). A higher-mode cache can serve a lower-mode request, but never the reverse. This prevents a quick-mode cache hit from satisfying an extended-mode request.

Semantic Matching

Questions are normalized by removing 60+ stopwords and normalizing 30+ synonyms (e.g., "database" → "db", "average" → "avg"), then sorted alphabetically. This gives identical semantic hashes for differently phrased versions of the same question.

Quality Gate

New results are staged, not immediately cached. A background worker evaluates quality via LLM scoring (completeness, accuracy, relevance, clarity, 1–10 each). Only results scoring ≥7 are promoted to permanent cache. Failures feed the anti-pattern tracker.

Knowledge Categories

8 categories enable targeted retrieval per injection point:

  • SCHEMA_DOCS — table/column documentation
  • BUSINESS_RULE — domain logic ("premium is calculated as...")
  • QUERY_TEMPLATE — proven SQL/Python patterns
  • DATA_QUALITY — known data issues ("column X has 30% nulls")
  • TERMINOLOGY — domain vocabulary
  • VISUALIZATION — chart patterns and best practices
  • WORKING_EXAMPLE — full worked examples
  • QA — known question-answer pairs

Embedding Providers

Three options: local sentence-transformers (all-MiniLM-L6-v2, 384 dims), LLM-provider embeddings (Gemini/OpenAI embed API), or BM25-only (no vectors). Auto-detected: tries local → LLM → none.

Async Reasoning Observer

The AsyncReasoningObserver runs as a parallel async task during agent execution, monitoring for anomalies without blocking the main pipeline.

Detectors

  • TimingMonitor: tracks phase durations against expected budgets
  • PatternDetector: identifies debug loops (same error repeated), empty results, and stuck states
  • CancellationToken: cooperative cancellation checked at plan/execute/synthesize boundaries

The observer reports are attached to the final state for diagnostics but do not interrupt execution unless cancellation is triggered.

Callbacks & Event Streaming

A CallbackManager provides a pub/sub event system. Nodes emit typed events (e.g., plan/start, execute/step_complete, deep/investigation_start) with structured data. Listeners can be attached for:

  • CLI progress: spinner, status messages, timing display
  • Web UI: real-time WebSocket streaming to the browser execution monitor
  • Logging: structured event logging

Design Patterns

Graph Orchestration

LangGraph-inspired directed graph of async nodes with shared TypedDict state. Conditional edges (escalation, replan), subgraphs for each mode. Not using LangGraph itself — custom lightweight implementation.

Factory Pattern

create_provider() instantiates the correct LLM provider based on a string identifier. API keys resolved from environment variables automatically.

Strategy Pattern

Each mode (quick, simple, extended, etc.) is a strategy implementing the same interface. dispatch_base_mode() selects the strategy based on classification.

Observer Pattern

CallbackManager implements pub/sub events. Nodes emit events; listeners (CLI, Web, logging) subscribe independently. Errors in listeners don't crash the pipeline.

Two-tier Cache

Exact-match (intent hash) + fuzzy-match (semantic hash) with quality-gated promotion. Staging → background LLM evaluation → promote/reject.

Subprocess Isolation

Generated code runs in separate processes with OS-level resource limits (memory, CPU). AST validation as a static analysis layer before execution.

Cooperative Cancellation

A CancellationToken is threaded through state, checked at major boundaries (plan, execute, synthesize). Enables clean timeout handling without killing subprocesses.

Metamode Composition

Deep and sequential modes compose base modes rather than reimplementing them. Each sub-question is independently classified and dispatched, with allowed_modes preventing recursive metamode invocation.
